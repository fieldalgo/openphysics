# 기여 안내

[English](../../../contributing.md) | **한국어**

OpenPhysics는 개발 중인 프로젝트입니다. [패키지 개요](overview.md)와
[구현·검증 계약](index.md)부터 확인하세요. `main`은
유일한 개발 줄기이자 기본 브랜치이며 pull request의 대상입니다. 기능 브랜치에는
아직 수용 검증을 통과하지 않은 작업이 있을 수 있습니다.

의심되는 버그, 정확도·연구 질문과 변경 제안을 환영합니다. 기존 이슈를 먼저
검색하고 가장 가까운 양식을 사용하세요. 확인된 관찰, 정확한 버전/커밋,
Python·운영체제 버전과 기대 동작을 적고 모르는 근거는 솔직하게 표시하세요.
완전한 재현 예제나 확정 결함은 도움이 되지만 이슈 등록의 필수 조건은 아닙니다.
main 동작과 PR 후보 동작을 구분하고 첨부 전에 인증정보·개인정보·기밀 모델을 제거하세요. 보안 취약점은
[보안 안내](security.md)의 비공개 경로로 신고하세요.

[개요·설치 안내](overview.md)에 따라 저장소 루트에서 설치·실행하세요.
고정한 Linux 검증 환경, 선택 도구·데이터와 격리 배포 검사는
[ci 한국어 안내](../../../../ci/docs/locales/ko/pages/README.md)를 따릅니다. GitHub Actions는 main push·Ready PR·명시적 수동 dispatch에서 실행됩니다.
기여 검증 시 정확한 workflow 결과와 artifact를 확인하세요.
직접 수행한 검사의 정확한 명령, 종료값, 실패와 선택 기능 skip을 기록하세요.

물리 기능 변경에는 독립 해석해와 메시 수렴 검사가 필요합니다. 기존 수치 기준을
유지하고 한계를 보고하세요. 제품 코드·주석·API·실행 예제는 영어로 작성하고,
사용법·검증 설명의 완전한 영어판과 한국어판을 함께 갱신하세요. 일부 시험의
통과나 문서 변경이 새로운 운영체제 지원을 입증하지는 않습니다.

변경 범위를 명확하게 유지하세요. 인증정보, 생성된 빌드 디렉터리, 로컬 환경 파일,
비공개 연구자료를 커밋하지 마세요. 원저작자 고지를 보존하고 새 의존성·데이터·복사한
코드의 이용 조건과 출처를 확인하세요. 기여에는 저장소의 [Apache-2.0](../../../../LICENSE)가
적용되며 제3자 자료의 예외는 [NOTICE](../../../../NOTICE)와 각 패키지 고지에 기록합니다.

기본 언어는 영어입니다. README와 기여·보안 진입 문서는 영어로 유지하고,
영어·한국어 문서와 언어 전환은 `docs/` 디렉터리 안에서만 제공합니다.

## 브랜치와 릴리스

PR은 draft로 엽니다. 브랜치 push와 draft PR에는 검증 실행기를 배정하지 않습니다.
적절한 로컬 또는 원격 환경에서 관련 검사를 수행하고 변경을 검토한 뒤 Ready로
전환합니다. 검토와 관련 검증을 마친 Ready PR은 모든 필수 검사를 유지하는 자동
Rebase and merge를 사용합니다.

main 검증은 고정 workflow/ref 그룹, `queue: max`, 취소 비활성화를 사용합니다.
다른 ref는 `queue: single`로 이전 실행을 대체합니다. Actions 대기열과 PR 병합
큐는 별개입니다.

경로·임시 디렉터리·subprocess·정리를 이식 가능하게 구현하세요. 전체 Linux
수용과 Linux·macOS·Windows 설치 배포 검증을 구분하고, 다른 OS의 통과나
universal wheel에서 플랫폼 지원을 추론하지 마세요. 정확한 실행·실패·artifact를 보존합니다.

`main`이 유일한 개발 줄기이자 기본 브랜치입니다. 최신 `origin/main`에서 기능
브랜치를 만들어 push하고 `main` 대상 PR을 엽니다. 공유·제출한 이력은 보존하고
다시 적용해야 한다면 새 브랜치를 사용합니다. 문서를 포함한 모든 변경은 GitHub
Actions의 `tests` 완료 검사(Linux source·배포·Studio와 세 설치 플랫폼)와 `windows-py312-thermal`이
성공해야 합니다. 배지뿐 아니라 정확한 후보의 로그와 artifact도 검토합니다.

초록 PR은 GitHub **Rebase and merge**로 반영합니다. 직접 push·merge 커밋·squash·
force-push·main 삭제는 차단하며 승인 리뷰 수는 0입니다. GitHub가 최신 main 위에
커밋을 새 해시로 다시 얹으므로 반영 뒤 main SHA를 기록합니다. 충돌하는 PR만 수동
rebase하고 재검증합니다. merge queue나 병합 전 결합 상태 재실행은 없습니다.
main push 실행이 결합 상태를 검사하며 뒤 push가 이를 취소하지 않습니다. 기능
브랜치·PR의 이전 실행은 대체될 수 있습니다. main 검증 실패를 조사하고 해당 상태를
릴리스하기 전에 PR로 수정하거나 되돌립니다. 병합된 기능 브랜치는 자동
삭제되므로 남은 작업은 병합 전에 별도 브랜치에 보존합니다.

다른 커밋에서 처음 작성한 작업을 새 기반에 다시 적용하거나, 다시 쓰거나, 제출 전에 squash하거나,
다른 기여자가 옮겨 반영할 때는 커밋 또는 PR 본문에 원본마다 `Ports: <sha>` 한 줄을 적습니다.
PR 자신의 커밋을 Rebase and merge로 반영할 때는 필요 없으며 PR이 그 기록을 남깁니다.
SHA만 적고 비공개 브랜치 이름이나 경로는 적지 않습니다. main의 조상이 아닌 커밋도 새 해시로
반영됐을 수 있으므로, 누락으로 보고하기 전에 `Ports:` 줄, PR 기록 또는 main의 동작을 확인합니다.

변경이 서로 의존하거나 충돌할 때만 임시 브랜치에 모으며 상시 통합 브랜치는 없습니다.
릴리스는 버전 변경을 같은 PR 절차로 반영한 뒤 결과 main 커밋의 필수 검사가 성공해야
`vX.Y.Z` 태그와 릴리스 노트·검증한 배포물을 게시할 수 있습니다. 브랜치 갱신만으로
패키지를 배포하지 않습니다. 현재 자동 PyPI·문서 사이트 게시가 구성돼 있지 않으며
인증과 게시 gate는 별도 설정이 필요합니다. 이미 배포한 버전의 패치가 필요할 때만
해당 태그에서 `maintenance/X.Y.x`를 만들고 main의 검토된 수정을 가져옵니다.

## 저장소 구조와 에이전트 진입 문서

여섯 구현 패키지는 각각 배포 이름·메타데이터·라이선스·고지를 유지합니다.
제3자 통합은 `gmshio`처럼 명시적 API와 외부 의존성 설명을 갖춘 별도 패키지에 둡니다.
Python은 `packages/` 안이 아닌 저장소 루트에서 실행하세요. 패키지 디렉터리 이름이
설치 모듈을 가려 비어 있는 namespace 패키지로 import될 수 있습니다.

이 기여 안내와 구현·검증 문서가 공통 기여 규칙의 원본입니다. `AGENTS.md`에는
짧은 탐색 안내·핵심 명령·기술적 주의점만 두고 `CLAUDE.md`가 이를 불러옵니다.
개인 선호·계정 설정·비공개 경로·세션 조율·운영 이력은 공개 저장소 밖에서 관리합니다.
