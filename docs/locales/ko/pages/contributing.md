# 기여 안내

[English](../../../contributing.md) | **한국어**

OpenPhysics는 개발 중인 프로젝트입니다. [패키지 개요](overview.md)와
[문서 색인](index.md)부터 확인하세요. 개발 환경, 검사, CI 결과 읽는 법은
[개발 안내](development.md)에 있습니다.

## 이슈 보고와 질문

의심되는 버그, 정확도·연구 질문, 변경 제안을 환영합니다. 기존 이슈를 먼저 검색하고
가장 가까운 이슈 양식을 사용하세요.

- 가진 관찰, 정확한 릴리스나 커밋, Python·운영체제 버전, 기대 동작을 적으세요.
  없는 근거는 솔직하게 표시하세요.
- 완전한 재현 예제나 확정된 결함은 도움이 되지만 필수는 아닙니다.
- `main`의 동작인지, pull request 후보에서만 생긴 동작인지 밝혀 주세요.
- 첨부하기 전에 인증정보, 개인정보, 기밀 모델을 제거하세요.

보안 취약점은 [보안 안내](security.md)의 비공개 경로로 신고하세요.

## 변경하기

[개요·설치 안내](overview.md)에 따라 저장소 루트에서 설치·실행하세요. Python은
`packages/` 안이 아니라 루트에서 실행합니다. 패키지 디렉터리 이름이 설치된 import를
가려 빈 namespace 패키지가 될 수 있습니다. 변경과 관련된 검사를 돌리고 정확한 명령,
종료값, 실패, 선택 기능 skip을 기록하세요. 일부 시험 통과가 필수 CI 검사를 대신하지는
않습니다.

- **물리.** 새로 추가하거나 바꾼 물리는 독립 해석 기준해와 메시 수렴 검사가 필요합니다.
  기존 수치 허용치를 유지하고 한계를 보고하세요.
- **언어.** 제품 코드, 주석, API, 실행 예제는 영어로 씁니다. `docs/` 아래 영어·한국어
  사용법과 검증 문서는 함께 갱신합니다. 저장소 README와 기여·보안 진입 문서는 영어로
  유지합니다.
- **플랫폼.** 파일 경로, 임시 디렉터리, 하위 프로세스, 정리 작업은 이식 가능하게 작성합니다.
  일부 시험 통과나 문서 변경이 새 플랫폼 지원을 입증하지 않으며, 한 운영체제의 통과나
  범용 wheel이 다른 운영체제의 결과를 뜻하지 않습니다.
- **범위.** PR 하나에 주제 하나. 같은 주제의 변경은 PR 하나에 모으고 변경마다 독립적으로
  읽히는 커밋 하나씩 두며, 주제가 다른 변경은 PR을 나눕니다. 기준은 CI 실행 횟수가 아니라
  나중에 읽는 사람이나 agent가 PR과 커밋만으로 무엇이 왜 바뀌었는지 따라갈 수 있는가입니다.
  인증정보, 생성된 빌드 디렉터리, 로컬 환경 파일, 비공개 연구 자료를 커밋하지 마세요.
- **라이선스.** 상위 고지를 보존하고, 추가하는 의존성·데이터·복사 코드의 조건과 출처를
  [제3자 소프트웨어](third-party.md)의 정책에 비추어 확인하세요. 그 휠에 묶인 것도 확인합니다.
  기여는 저장소의 [Apache-2.0 라이선스](../../../../LICENSE)로 제출되며, 제3자 예외는
  [NOTICE](../../../../NOTICE)와 패키지 고지에 기록합니다.

## Pull request와 반영

`main`은 유일한 개발 줄기이자 기본 브랜치입니다. 기능 브랜치에는 아직 수용 검증을
통과하지 않은 작업이 있을 수 있습니다.

1. 최신 `origin/main`에서 기능 브랜치를 만들고 `main`을 대상으로 pull request를
   **draft**로 엽니다. 브랜치 push와 draft PR에서는 검증이 돌지 않습니다.
2. 변경을 검토하고 관련 검사를 돌린 뒤 **Ready for review**로 바꿉니다. 검증은 Ready PR,
   main push, 명시적 수동 실행에서 돕니다.
3. 문서만 바꾼 변경을 포함해 모든 변경에 필수 검사 **`tests`**가 필요합니다. 배지만이
   아니라 해당 실행의 로그와 artifact를 확인하세요. 검사 범위는
   [개발 안내](development.md#ci가-돌리는-것)에 있습니다.
4. 통과한 PR은 GitHub **Rebase and merge**로 반영합니다. 자동 병합은 검토와 관련 검증을
   마친 뒤, 모든 필수 검사를 유지한 채로만 켭니다. 승인 리뷰는 필요하지 않습니다. 직접 push,
   merge commit, squash merge, force push, `main` 삭제는 막혀 있습니다.
5. GitHub는 커밋을 최신 `main` 위에 새 커밋 ID로 다시 적용합니다. 반영된 `main` SHA를
   기록하세요. 충돌한 PR만 수동 rebase와 재검증이 필요합니다. merge queue나 반영 전 결합
   상태 재실행은 없으며, `main` push 실행이 결합 상태를 검증하고 이후 push로 취소되지
   않습니다. 실패한 `main` 실행은 조사해서 해당 상태를 릴리스하기 전에 PR로 수정하거나
   되돌리세요.

병합된 기능 브랜치는 자동으로 삭제됩니다. 남은 작업은 병합 전에 별도 브랜치에 보존하세요.
공유되거나 제출된 이력은 보존하고, 다시 적용해야 하면 새 브랜치를 쓰세요. 서로 의존하거나
충돌하는 변경만 임시 브랜치 하나로 합치며, 상시 통합 브랜치는 없습니다.

**옮겨 온 작업.** 다른 커밋에서 먼저 작성한 작업을 반영할 때(새 기준에 다시 적용, 재작성,
제출 전 squash, 다른 기여자의 이식)는 커밋이나 PR 본문에 원본마다 `Ports: <sha>` 줄을
하나씩 적고, 비공개 브랜치 이름이나 경로는 쓰지 마세요. Rebase and merge로 반영된 PR 자신의
커밋에는 이 줄이 필요 없습니다. `main`의 조상이 아닌 커밋도 새 ID로 반영됐을 수 있으니,
없다고 보고하기 전에 `Ports:` 줄, PR 기록, `main`의 동작을 확인하세요.

## 릴리스

배포판 아홉 개는 버전 하나를 함께 씁니다. 버전 변경은 모든 패키지의 버전을 바꾸고, 패키지
사이의 의존성을 그 마이너 계열 안에 두고, [변경 기록](changelog.md)의 `[Unreleased]` 절에
날짜를 붙입니다. `tools/check_release_version.py`가 이를 확인합니다. 버전 변경을 같은 PR
절차로 반영하고, 그 `main` 커밋의 필수 검사가 성공한 뒤 `vX.Y.Z`
태그를 달고 릴리스 노트와 검증한 배포물을 공개합니다. 릴리스 배포물은
`OPENPHYSICS_DOCS_REF`를 그 태그로 두고 빌드해야 PyPI 설명이 릴리스된 파일로 연결됩니다
([개발 안내](development.md#배포pypi) 참고). 브랜치 갱신이나 태그만으로는 패키지가
배포되지 않습니다. GitHub 릴리스를 게시하면 `Release` 워크플로가 시작되고, 릴리스 커밋의
검증이 성공한 뒤에만 PyPI에 올립니다. 먼저 `main`에서 손으로 실행해 dry run을 하세요. 그때는
아무것도 올리지 않습니다. 문서는 자동으로 게시되지 않습니다. `maintenance/X.Y.x`는 해당 릴리스에 패치가 필요할 때만
릴리스 태그에서 만들고, 검토된 수정을 `main`에서 가져옵니다.

## 저장소 구조

구현 패키지 여덟 개는 배포 이름, metadata, 라이선스, 고지를 각각 유지합니다. 제3자 연동은
`gmshio`처럼 명시적 API와 문서화된 외부 의존성을 갖는 별도 패키지에 둡니다. GPL 프로그램은
선택 extra로 설치되는 별도 프로세스로만 그런 연동을 뒷받침할 수 있습니다(`gmshio[gmsh]`가
Gmsh를 설치하듯). import·링크·번들하지 않습니다.

이 안내와 구현·검증 문서가 공통 기여 규칙을 담습니다. `AGENTS.md`는 짧은 안내, 핵심 명령,
기술적 함정을 담고 `CLAUDE.md`는 이를 가져옵니다. 개인 설정, 계정 설정, 비공개 경로, 세션
조정, 운영 이력은 공개 저장소 밖에 두세요.
