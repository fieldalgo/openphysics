# 영역 Studio 자원 관측

[English](../../../region_resource_probe.md)

`tools/studio_resources/run_region_resource_workloads.py`는 재료 영역이 있는 열전도
문서([Studio 영역 문서](packages/simcase/thermal_studio.md#영역-문서))를 받는 Studio를
측정합니다. 작업마다 정확한 소스 checkout의 Studio 서버를 새 loopback 프로세스로 띄우고,
capability를 요청하고, 문서를 검증하고, 검증이 받아들이면 실행해 job을 polling합니다.
성능 기준이 아니라 관측입니다. 작업의 결과 코드가 아래에 정해 둔 것과 다르거나 단계가
실패할 때(서버가 뜨지 않음, 예상하지 않은 HTTP 상태, 300 s 기한)만 실패합니다. 메모리
값을 `/proc`에서 읽으므로 Linux 전용입니다.

```sh
python tools/studio_resources/run_region_resource_workloads.py --source-root . --expected-commit FULL_CHECKOUT_SHA --output .validation/region-resource-observation
```

Checkout은 지정한 commit이어야 하고 `packages/`와, 모든 문서를 만드는
`tests/simcase/region_studio_fixtures.py`에 변경이 없어야 합니다. 서버는 checkout의 패키지
소스를 `PYTHONPATH` 앞에 두고 실행하며, 1차 모듈이 다른 곳에서 오면 서비스를 거부합니다.
네이티브 thread 변수 여섯 개를 1로 둡니다. `--workload NAME`(반복 가능)은 로컬 작업용으로
일부만 실행합니다. CI는 과도 관측 뒤에 전체를 한 번 실행합니다.

## 기록하는 것

작업마다 생성한 문서와 서버 stderr 옆의 `region-workloads.json`
(`region-resource-workloads-v1`)에 다음을 기록합니다.

- 결과: `done`, `validate:<코드>`(검증 거절), `job:<코드>`(job 오류)와 기대 결과;
- Studio가 검사하는 방식 그대로 관측 도구 자신의 프로세스에서 checkout의 simcase로 센
  문서의 개수: 도형, 원, 다각형 점; 이 셋이 Studio 한도 안이면 경계 교차; 교차도 한도
  안이면 루프 꼭짓점;
- client가 잰 검증 요청의 wall time;
- 실행이면 run 요청의 wall time(다시 검증함), 받아들여진 run부터 종료 상태까지의 job wall
  time, 가장 느린 상태 polling;
- 두 번째 client thread가 검증 요청 동안, 그리고 run 요청부터 종료 상태까지 100 ms마다
  보내는 capability 요청에 대한 가장 느린 응답: 검증이나 job이 인터프리터를 쥐고 있는
  동안 서버 event loop가 얼마나 응답하지 못했는지(로컬 실행에서 20 ms마다 보내면 job이
  최대 약 25 % 느려졌음);
- 결과의 인코딩 byte 수;
- capability 요청 직후(유휴) 서버 VmRSS, 끝의 VmHWM, 그 차이.

VmHWM은 프로세스 최고 수위이므로 시작과 검증도 포함합니다. 시간에는 loopback HTTP와
polling이 들어갑니다. 공유 호스트에서 한 번 잰 값은 용량 주장이 아니며 한도는 계속
`candidate-unmeasured`입니다.

## 작업과 기대 결과

기대 결과는 도구에 고정되어 있으며 결과가 다르면 실행이 실패합니다.

| 작업 | 기대 |
| --- | --- |
| 정상 예제, 메시 크기 2 mm | `done` |
| 정상 예제, 메시 크기 0.4 mm(절점 약 9800개) | `done` |
| 메시 크기 1000 mm 배경 안의 높이 0.2 mm, 크기 0.06 mm 띠 하나 | `done` |
| 같은 띠를 높이 0.005 mm, 크기 0.01 mm로 | `job:mesh_limit_exceeded` |
| 정상 예제에 길이 30 mm, 두께 1e-7 mm 강철 막 추가 | `job:mesh_limit_exceeded` |
| 고립된 원 16개, 사각형 47개, 512각형(도형 64개, 점 512개) | `done` |
| 전역 크기 0.025 mm, 배경과 판 크기 2 mm인 정상 예제 | `done` |
| 이가 63개씩인 교차 빗 두 개(점 510개) | `validate:geometry_limit_exceeded` |
| 교차가 1024 안에 드는 가장 많은 이를 가진 덮인 교차 | `done` |
| 같은 것에서 앞쪽 사각형 16개 대신 덮는 사각형 뒤에 똑같은 원 16개 | `done` |
| 이 126개인 덮인 교차(사각형 4개 밑에 숨은 교차) | `validate:geometry_limit_exceeded` |
| 같은 직선 위 겹침: 두 직선을 따라 점을 나눈 512점 다각형, 같은 직선 위 사각형 47개, 똑같은 원 16개 | `done` |
| 고립된 원 16개 뒤의 서로 교차하는 32점 별 16개 | `validate:geometry_limit_exceeded` |
| 끝 각이 약 1도인 511점 톱니 하나 | `job:solver_failed` |
| 끝 각 10도, 흔든 톱니와 교차 사각형 60개, `min_angle` 33 | `job:mesh_limit_exceeded` |
| 0.3 mm 간격, 크기 0.15 mm, `min_angle` 33인 동심 고리 7개 | `job:solver_failed` |
| 과도 예제, 시간 9개, 메시 크기 0.2 mm | `done` |
| 과도 예제, 시간 64개, 메시 크기 0.5 mm | `done` |
| 과도 예제, 시간 128개, 메시 크기 0.25 mm | `job:history_limit_exceeded` |

교차 한도가 없으면 덮인 교차는 `Document.from_dict` 하나에만 18.5 s와 32 s(두 번 측정)가 들고, 검증과 실행이
이를 되풀이합니다([호출자를 위한 메시 상한](packages/simcase/thermal_regions2d.md#호출자를-위한-메시-상한) 참고).
세 교차 문서는 이제 `Document.from_dict` 전에 멈춥니다. 맞닿은 경계와 같은 직선 위
겹침(공유한 변, 똑같은 원)은 경계 교차가 아니므로 `max_boundary_crossings`가 세지 않지만,
도형 boolean은 여전히 비싸게 만듭니다. 이것으로 만든 두 작업이 아래에서 가장 느린 검증입니다.
띠·막·끝 10도 톱니 작업은 절점 한도보다 훨씬 촘촘한 메시가 필요하므로 job 안의 과밀 메시 거절에
드는 비용을 보여 줍니다. 끝 1도 톱니도 그런 메시가 필요하지만, simcase가 메시를 만드는 마이크로미터
사본에서 meshine이 먼저 그 경계를 거절하므로("cannot resolve", 안전한 실패) 1 s 안에
`solver_failed`로 끝납니다. 이 작업의 결과는 처음에 `job:mesh_limit_exceeded`로 정했습니다.
밀리미터로 메시하면 절점 한도에 닿기 때문입니다. 마이크로미터 메시로 처음 실행했을 때 이 작업이
실패해 `job:solver_failed`로 바꿨고, 처음 정한 기대는 실패합니다. 원인은 척도가 아니라 밀리미터에서
마이크로미터로 바꾸는 배율 1000입니다. 사본에서 meshine은 톱니 변 56개의 중점에 같은 자리나
7e-12 µm 이내에 점 두 개를 넣고, 삼각분할은 이를 구분하지 못합니다. 모든 길이에 0.001, 0.5, 2, 3, 7,
10, 100, 999, 1001, 1024, 1e6을 곱해 그대로 메시하면 절점 한도에 닿고, 1000을 곱하면 같은 방식으로
실패합니다. 상한도 Studio도 없이 simcase로 이 문서를 실행해도 같은 오류가 납니다. 동심 고리는 job이
끝나는 또 다른 방식을 보여 줍니다. 절점 한도가 멈추기 전에 meshine의 세분이 80 round 안에 수렴하지
않으며 job은 `solver_failed`로 끝납니다.

CPU 4개, 네이티브 thread 1)에서 이 도구·fixture·패키지로 한 번 측정했고, 작업 열아홉 개에
147 s 걸렸습니다. 모든 결과가 기대한 것과 같았습니다. 시간은 client wall time(s)이며, 검증은

이 실행에서 과밀 문서(띠, 막, 끝 10도 톱니)는 job에서 0.8~2.9 s 동안 메시를 만든 뒤
거절되었고, 끝 1도 톱니는 0.3 s, 동심 고리는 11.7 s 뒤에 끝났습니다. 그 전의 마이크로미터 메시
실행 두 번에서는 각각 0.8~3.0 s, 0.3~0.4 s, 10.6~12.7 s였습니다. simcase가 영역 문서를
마이크로미터로 메시하기 전의 앞선 로컬 실행들은 과밀 문서(끝 1도 톱니 포함)를 더 빠른
호스트에서 0.4~3.8 s, 이 호스트에서 0.7~5.3 s 뒤에 거절했고, 동심 고리는 6.1~6.9 s와 9.7 s
뒤에 끝냈습니다. 가장 느린 capability 응답 0.48 s는 job이 도는 동안 나왔고, 검증 중에는 최대
0.05 s(앞선 실행들에서는 최대 0.06 s)였습니다. 결과 byte는 실행마다 몇 byte 다를 수
있습니다. 공유 호스트에서 한 번 잰 값이며 보장이 아닙니다. CI 실행은 자기 값을 기록합니다.
